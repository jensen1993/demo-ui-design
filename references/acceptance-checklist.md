# Demo acceptance and delivery gates

Use this checklist for every requested demo before calling it complete, and again at the relevant stage of an authorized publication. It coordinates the existing detailed references rather than replacing them. Apply only to the deliverable and features actually requested: a static mockup does not need runtime package checks, and an unrequested publication is not applicable. Honor explicit user instructions and existing-project constraints; record their effect rather than inventing extra features.

## Method and statuses

1. Derive the target PC/mobile browser, requested flows and requirement coverage. Select representative pages: entry/home, main list or dashboard, detail/form and a resulting state when present. Check each applicable row below. For feature-specific checks include every requested critical flow, not just a homepage screenshot. Use the actual preview URL and real generated build; keep a short evidence record in the work output or final answer, with commands/results or page, viewport, action and observation as appropriate.
2. Record a separate status for each applicable subcheck in the table and in the subcheck list below: **PASS** = checked and met, with evidence; **FAIL** = checked and not met; **NOT CHECKED** = applicable but no reliable evidence, with reason; **N/A** = genuinely outside requested scope, with reason. If a parent row is summarized, derive its status in this order: any FAIL → FAIL; otherwise any NOT CHECKED → NOT CHECKED; otherwise at least one PASS → PASS; all N/A → N/A. Do not let a parent summary hide mixed results. An intentional justified departure from a numeric layout heuristic may pass when documented and the actual experience remains usable. A skipped check, guessed source, unavailable browser, screenshot without interaction, or zero audit inputs is never a pass.
3. For each failure, fix the cause and repeat the affected checks, recording the final result. Report any not-checked or failed row and its practical impact. If a blocking condition below remains or its essential proof is unavailable, do not call the result completed or publish it by default. Return useful partial work as **incomplete**, explain the concrete blocker and evidence missing, and provide local preview/source only where feasible. Handle explicit requests for incomplete publication under the exception policy below; do not conceal a blocker by relabeling it N/A.

## Independent subchecks for mixed outcomes

Always report these individually when applicable, even if the parent is summarized. Each line needs its own evidence or reason. A parent status of NOT CHECKED due solely to an optional subcheck does not automatically block delivery; apply the gates to the specific subcheck and observable impact.

- **B1** build/start command; **B2** open the correct project and routes. B2 is blocked if browser evidence is unavailable, even when B1 passes.
- **C1/D1** UI/icon dependency or actual files; **C2/D2** source import and usage; **C3/D3** visible rendering. Check and report C and D independently.
- **E1** navigation; **E2** search/filter; **E3** forms/validation; **E4** create/update and resulting state; **E5** simulation labels. Mark genuinely absent features N/A, not PASS.
- **F1** browser inspection at representative viewport sizes (essential); **F2** geometry measurements and layout-script result (optional only when unavailable, disclose what was and was not measured); **F3** essential hit areas, clipping, overflow and fixed bars. A numerical zero-finding result alone is not sufficient evidence for F1 or F3.
- **G1** type size/weight/line height and hierarchy; **G2** actual contrast measurement; **G3** text resize or zoom (state which); **G4** focus and icon-only accessible names. Each is PASS, FAIL, NOT CHECKED or N/A independently. An unavailable optional contrast or resize test does not erase another subcheck's result; disclose the limitation and do not claim accessibility compliance. Observed illegibility, failed applicable contrast, or unusable essential controls remain blocking as in G.
- **H1** imagery match/quality; **H2** data relationships and units; **H3** source/license or generated provenance and honest simulation labels. An unavailable image does not automatically make H2 fail.
- **J1** pre-publication build/archive; **J2** unambiguous target and distribution rights. **K1** service publication response; **K2** independently open actual URL, main route and assets. K2 must remain NOT CHECKED if network access is unavailable, even when K1 passes.

If no browser, package installation or other essential capability is available, say whether implementation/build succeeded, identify exactly which checks are blocked, provide the feasible local preview or source, and state the concrete next action (for example, run browser checks on an equipped computer or install the missing packages). Do not describe the work as fully accepted or publish it by default when a blocking subcheck is failed or not checked. This is a quality gate, not a reason to stop useful reversible work.

## Exceptions and release decision

- **Normal completed demo:** all applicable blocking checks pass. An explicitly requested static design, an existing-project restriction or a user-requested alternative is evaluated against that actual scope and noted; do not add libraries just to meet a checkbox when the user has expressly excluded them.
- **Genuine external blocker:** try feasible compatible alternatives within scope, then record what was attempted and what is unavailable. A missing component library, Font Awesome, essential image or essential browser validation remains FAIL or NOT CHECKED; provide any honest partial demo as incomplete, without calling the default requirements passed and without publishing it as complete. Explicitly disclose any fallback and its impact. Do not seek extra approval merely to report or hand over reversible partial work.
- **Nonblocking limitation:** a missing optional measurement or device test, or a justified numeric layout deviation with an otherwise usable result, must be reported as NOT CHECKED or as an evidence-backed exception; it is not grounds for inventing an automatic pass or claiming native-device, Apple certification or WCAG conformance.
- **Explicit user direction:** user-specified changes to scope and deliverable take precedence. If the user expressly wants an incomplete preview or publication with a known non-safety quality limitation, describe the remaining failures accurately; never conceal a known issue or represent a failed check as passed. Do not publish known secrets or unauthorized private material.

## Compact delivery record

Provide a compact per-row table or equivalent, e.g. `A PASS — feature map: ...`; `F NOT CHECKED — browser unavailable`; `J N/A — user did not request publication`. Include actual UI library/component and Font Awesome icon evidence, representative pages/viewports/actions, image/data provenance, build result, accessible preview or returned URL, failures/fixes/rechecks, and unverified checks. Separate local acceptance, publication response and online reachability. Record measurements and their source; never invent screenshots, results, real-device testing, legal rights or tool calls. Skill instructions alone cannot force another model to comply; the evidence record makes execution reviewable.
