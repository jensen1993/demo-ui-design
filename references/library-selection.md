# Reference and component selection

A design system, a web component package, and a native mobile implementation are different things. First follow the user's explicit choices and existing project conventions. Select one main visual system; borrow complementary interaction principles without mixing incompatible visual styles indiscriminately.

| Scenario | Primary reference | Implementation considerations |
| --- | --- | --- |
| PC admin, CRM, ERP, order or operations management | TDesign: https://tdesign.tencent.com/ or Ant Design: https://ant.design/ | Vue projects can use a compatible TDesign implementation; Ant Design is primarily React. Select based on the stack and existing components. TDesign Starter https://tdesign.tencent.com/starter has business examples. |
| PC desktop application demo | Browser-compatible TDesign, Ant Design, or shadcn/ui according to the chosen web stack | Present a desktop-application-like experience in a PC browser by default. Package with an existing/requested desktop runtime only when explicitly requested. |
| PC SaaS, dashboard, modern tool, startup website | shadcn/ui https://ui.shadcn.com/ and https://ui.shadcn.com/blocks | A good fit for React/Tailwind-compatible projects. For other stacks translate layout and design ideas into that stack; do not add React just to use it. Marketing sites may need custom layouts and visual assets. |
| Mobile App, H5, or mini-program demo | Browser-compatible TDesign Mobile Vue or Ant Design Mobile React; use Apple HIG / Material for interaction guidance | Default to a mobile browser demo even if the brief describes an App or mini-program. Choose a library that runs in the actual web stack; represent relevant platform navigation, safe-area and interactions. A browser demo is not a packaged app or mini-program. |
| Existing project or explicitly requested target-specific package | Existing compatible UI library first; uni-ui, Wot UI or uv-ui for compatible uni-app; React Native Paper or Elements for compatible React Native | Preserve explicit stack and scope; check component, version and target compatibility. Only create native or mini-program packages when explicitly requested. |

For visual inspiration, Mobbin https://mobbin.com/ and Dribbble https://dribbble.com/ may be consulted when accessible; they are third-party showcases, not open-source asset bundles. Account, access and copyright restrictions may apply. Never rely on them being accessible. Recreate general layout principles rather than copying proprietary screens or assets. Official references above and local project assets are sufficient fallback.

## Decision order and resource availability

1. Explicit user direction and existing brand, runtime, and installed UI packages take priority. For an existing app, extend them instead of replacing them for a demo.
2. Identify the intended experience (PC desktop/web, phone app/H5 or specific mini-program) and its actual delivery runtime. For a new demo, the runtime is the browser unless the user explicitly requests otherwise. A phone-sized browser demo must not be represented as a native app or a published mini-program.
3. For React admin, prefer Ant Design for data-heavy business components or shadcn/ui for a custom SaaS visual; for Vue admin consider TDesign. Existing compatible components and explicit requests take priority.
4. For mobile App and mini-program demonstrations running in a browser, select a compatible mobile-web library for the chosen Vue or React stack. Use Apple HIG and Material as platform interaction guidance, not proof that an app or mini-program has been built. Use uni-app, React Native, native tooling or an actual package only when an existing project or explicit request calls for it.
5. For runnable implementation, integrate and actually use the chosen compatible UI library: inspect package metadata, uni_modules or equivalent, and page source; run a feasible build/preview. Existing compatible UI libraries satisfy this requirement. Base framework widgets, Font Awesome icons or styling inspired by documentation alone do not. If no compatible library can be installed because of a real restriction or unavailable environment, report the blocker and use an honest fallback instead of claiming success. Use local dependencies/assets first. These references are links, not bundled libraries: if network access, package installation or licensed assets are unavailable, use compatible existing dependencies, locally licensed SVG icons or CSS building blocks and disclose the fallback. Do not claim to have used a component library just because its visual principles informed the layout.

## Font Awesome Free

- Browse https://fontawesome.com/search with the free filter and consult https://docs.fontawesome.com/ for the project's exact version and platform. Verify the specific icon and style are in the installed Free package; Free Solid, Free Regular and Brands do not necessarily have identical coverage. Pro styles and icons need appropriate existing authorization and access.
- Use an integration compatible with the stack (for example, the official React/Vue packages on web or an appropriate Flutter/React Native package for native apps), and follow project conventions. Use existing packages when available; use supported icons and avoid loading a whole icon collection unnecessarily. If a package is unavailable for a target, use a compatible existing library or licensed SVGs with notices; explain the fallback.
- Keep icons visually consistent in size, weight and alignment. Decorative icons should be hidden from assistive technology; icon-only controls need accessible names. Font Awesome Brands are useful for third-party brand marks, subject to the relevant brand's trademark guidelines.
- Free does not mean the licenses are identical: fonts, icons and code may have different terms. When distributing copied assets or bundles, retain the applicable license and notices from the exact package. Do not bundle Pro assets or third-party paid resources without authorization.

## Required integration and evidence for runnable demos

- For a new runnable demo, select a compatible real component library and Font Awesome Free before building; install or reuse actual compatible packages/assets, then render both on visible pages. Choose components suited to the interaction, such as search/input, button, tabs, popup or form; use more than an isolated token component where the interface calls for several. Apply Font Awesome icons to relevant visible controls or navigation; do not replace meaningful product photography with icons. Library-native icons may coexist, but do not silently substitute for Font Awesome.
- For an existing project, reuse its compatible component library and preserve its conventions. An explicit user instruction to avoid or use a different library takes precedence; avoid disruptive dependency changes to an established project. A static mockup, requested no-dependency format, incompatible runtime, unavailable packages or offline environment may prevent integration: record the actual exception and report the requirement as unmet or not applicable, with the fallback. Do not manufacture an exception just to avoid integration.
- Before claiming completion, check (1) dependency manifest, lockfile or installed local package/asset and license, (2) actual imports and usage in page source, including the exact component and Free icon names, and (3) visible rendering and a working preview or build, with the pages/actions checked. An icon package declared but never rendered or a UI package installed but never used does not pass. When copied, local components (such as shadcn/ui) are used, cite the actual component files and imports rather than expecting a package name. Font Awesome may render as SVG, webfont or framework components; identify its source rather than assuming all SVGs are equivalent.
- Report a compact evidence record in the delivery: UI library + version/source, two or more representative actual component usages where applicable; Font Awesome Free + actual visible icons and page; preview/build result; exceptions and unverified checks. For an existing project with only one relevant control or a design-only request, explain what applies instead of creating pointless UI. Do not equate loading a CDN, a logo, text stating a library name, or visual similarity with proof of component usage. If a package cannot be installed or tested, say so and do not label it verified.
- These are instructions, not a technical enforcement boundary: another model may ignore them. Run the checks yourself when possible and retain verifiable evidence for review; do not assert compliance merely because the skill was invoked.
