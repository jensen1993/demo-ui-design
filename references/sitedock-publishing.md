# Publishing browser demos with SiteDock

Use this workflow when the user asks to publish, deploy, share a hosted demo, or explicitly requests SiteDock. An ordinary request to make or locally preview a demo is not by itself authorization to publish it online. If the user requests a different hosting provider, follow that choice.

Before uploading or publishing, complete the applicable pre-publication gates in [acceptance-checklist.md](acceptance-checklist.md). By default, do not publish with an unresolved blocking issue; report the incomplete result and blocker. Handle explicit user requests for incomplete publication as described in that checklist. After publishing, perform and record the separate online checks; do not report online reachability as passed when it has not been checked.

1. Discover SiteDock tools in the current host rather than assuming the tool names or connector exist in all AI products. When available and sufficient, use them instead of browser automation. If unavailable, explain that this environment needs a SiteDock connection or another authorized hosting method; finish the local browser demo and provide preview/restart instructions. Do not claim that installing this skill itself installs SiteDock or grants account access.
2. Build and test the actual complete static browser output, with `index.html` at the archive root, suitable asset paths and SPA fallback when needed. Inspect the output and exclude source secrets, credentials, private data, irrelevant files and dependencies. A static host cannot run a backend: preserve honest simulated behavior and report any limitations. Verify image assets and licensing for distribution.
3. If publication is requested but the target is unspecified, create a new site when the context reasonably indicates a new demo. If the user asks to update an existing site, identify it unambiguously via accessible site listing; do not overwrite a site when its identity is unclear. Publication to an existing site is a complete replacement, so archive all necessary build output, never upload an incremental subset, and preserve its site ID. Ask for clarification if unsure which existing site to replace. Do not delete or take sites offline unless expressly requested.
4. Follow the current SiteDock tool descriptions: request the temporary single-use upload URL, ZIP only the completed static directory contents so index.html is at the archive root, upload ZIP bytes using the supported HTTP PUT method, then publish with the upload ID and appropriate site ID/name and SPA setting. Do not send a local file path as though the remote service can read it. Never print the temporary upload URL or credentials. If the runtime cannot upload a file, explain the SiteDock dashboard ZIP-upload fallback.
5. Report publication only after the service returns success; include the actual returned site name and accessible domain aliases, and report any cleanup warning. Test the returned URL and the main route on the public site when network access permits; distinguish a successful publish response from independently verified DNS/TLS and page reachability. Report failures and any unverified checks honestly. For updates, understand the server may remove the old version after success; do not imply an automatic rollback is available.
