# Demo UI design

Create a coherent, attractive, credible demo for the requested product and audience across the requested PC website, PC desktop app, mobile app, H5 or mini-program target. Treat the work as a demo: focus on a reviewable experience, realistic example data and the requested flows, rather than assuming production integrations or production readiness. By default deliver a working browser-openable interactive demo: desktop browser for a PC interface and phone browser for an App, H5 or mini-program interface. Platform names describe the intended experience, not a request to build or package that platform. If the user explicitly requests a static design, native build, mini-program package or an edit to an existing project, honor that request instead. Do not claim a browser demo is a native app, real mini-program, or a device test. Do not change the product's scope or introduce unrelated features.

## Approach

For a runnable demo, follow this order: (1) identify scope and target; (2) choose and actually use a compatible component library and Font Awesome Free; (3) build the requested flows with fitting typography, images and example data; (4) run the acceptance checklist and fix blocking issues; (5) publish only when requested and recheck the online URL; (6) report evidence, failed or untested items and next steps. Read the linked references for the actual rules; this order is a guide, not a replacement for them.

1. Determine the product scenario, target devices, deliverable, visual preferences, and existing project stack. Inspect existing UI, dependencies, assets, and instructions before selecting libraries. Infer reasonable defaults and proceed when details are missing; respect explicit choices and the existing brand. For a new mobile App demo with no requested visual style, default to iOS-inspired interaction polish while accommodating Android safe areas and interaction conventions; choose colors and visual identity for the actual business rather than a fixed palette. An explicit platform/style and an established project design take precedence; do not describe an iOS-inspired design as native iOS controls or device validation.
2. Read [references/library-selection.md](references/library-selection.md). For a new demo without a specified implementation stack, choose a suitable web stack and a compatible UI component library for browser delivery; do not ask nontechnical users to pick a framework. An App or mini-program request ordinarily determines the mobile screen, navigation and platform-appropriate interactions, not a requirement for uni-app, native SDK, developer tools or a package. Respect explicit stack and packaging requests and established project constraints. State the chosen implementation and preview method in plain language.
3. For an implementation, actually integrate the selected compatible UI component library and use its relevant components in the visible working pages. Reuse an existing compatible library first; do not add a second just to satisfy this rule. Do not count raw framework primitives, icons alone, copied styling, or documentation links as integrating a component library. Verify dependency/configuration or installed component files, actual component usage, and an appropriate build or preview. If a requested format, explicit restriction, unavailable network/tooling, or compatibility prevents integration, deliver the best feasible result and clearly report the blocker and what was used instead; never claim a library was integrated without evidence.
4. Use Apple Human Interface Guidelines as the foundational reference for layout and control hierarchy across demos; read [references/apple-layout-foundation.md](references/apple-layout-foundation.md), [references/design-baseline.md](references/design-baseline.md), and [references/typography.md](references/typography.md) for platform-appropriate defaults and checks. Use the typography reference's semantic font/size/weight/line-height defaults and its browser review procedure; for mobile screens also read [references/mobile-patterns.md](references/mobile-patterns.md); for iOS, an iOS-style demo, or the default new mobile App style read [references/ios-style.md](references/ios-style.md). Read [references/visual-direction.md](references/visual-direction.md) and establish a distinctive visual direction and palette suited to the actual business, audience, content, platform and brand; compare multiple credible directions before choosing, avoiding habitual palettes and layouts. Plan page hierarchy, type, color, spacing, imagery, icon style, and interaction states together. Prefer a distinctive and coherent result over generic dashboard cards or a uniform template. Select relevant examples from [references/demo-patterns.md](references/demo-patterns.md).
5. Build or design the requested demo. When a requirements document is supplied, map its individual features to screens and identify which are interactive, simulated, visual-only or omitted; preserve important fields, roles, rules and status transitions rather than treating a module heading as full coverage. Present the coverage in an appropriate concise form. Read [references/demo-data.md](references/demo-data.md); use scenario-specific, internally consistent sample content and appropriate imagery, not generic placeholders or invented claims presented as facts. Demonstrate requested flows with working controls and coherent local demo data when feasible; if a visible action is only an entry point or cannot be simulated, label it honestly and do not present it as complete; do not imply a backend or payment integration exists. Keep normal, empty, loading, and error states where relevant to the requested flow. Meet readable contrast, visible keyboard focus on web, touch-friendly controls, responsive layouts, and safe areas on mobile.
6. For a new runnable demo, actually integrate Font Awesome Free and render its suitable icons on visible working pages, in addition to the UI component library. A library’s own icons, hand-drawn SVGs or merely adding a package do not satisfy this requirement. Follow the integration and exception rules in [references/library-selection.md](references/library-selection.md); respect explicit user choices and avoid disrupting an established project. Verify the exact Free icons and styles; never assume Pro is available.
7. Verify the result to the extent feasible: run appropriate project checks, exercise the main demo flow including data updates and search/filter or validation when applicable, and inspect the working browser preview at representative PC or mobile sizes when available. Follow [references/layout-audit.md](references/layout-audit.md) for measured heading/action alignment, grouping, gaps, card edges, touch targets and density at relevant browser viewport sizes; run its script when supported, fix or explain flagged issues, then recheck. Also perform the Apple-informed visual review; numerical checks alone are not proof of good design. Confirm that explanatory copy and advertised actions match what the demo actually does. Use the actual URL reported by the preview server, confirm its title/content matches this project (ports may already be occupied), and give a usable preview link plus restart instructions when needed. Report what was actually verified and any missing visual or device checks. Do not claim real device validation without it. Clearly distinguish a browser mockup from an actual desktop app, App build or mini-program build, and report the accessible preview and what was not verified.

Before claiming completion or publishing, read and apply every applicable row of [references/acceptance-checklist.md](references/acceptance-checklist.md). Record pass/fail/not applicable/not checked, evidence, and any fixes/rechecks; follow its blocking and incomplete-delivery rules. If a blocking item is unresolved, do not present the demo as complete or publish it by default; report the partial work and blocker. Static-only design and other explicitly requested exceptions are assessed against their actual scope. These instructions do not supersede an explicit user request or existing-project constraints; handle an explicit request for an incomplete publication as described in the checklist.

For a user-requested online publication, discover and use SiteDock when available; follow [references/sitedock-publishing.md](references/sitedock-publishing.md). A browser preview or ordinary demo request does not by itself authorize public publication.

Before delivery, follow the evidence checklist in [references/library-selection.md](references/library-selection.md) and the image/data review in [references/demo-data.md](references/demo-data.md). If a default requirement cannot be fulfilled, report it as unmet, the concrete blocker and the fallback; do not silently substitute. Keep the final explanation concise and accessible: identify the actual UI and icon libraries, real visible component/icon examples, image/data sources or simulation, what works, and what was verified. Distinguish dependency, page usage and rendered preview evidence; never claim verification that was not performed. Do not present a source reference as an installed dependency or a pixel-perfect match unless verified.
